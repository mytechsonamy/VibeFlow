# The Product Bible

A project is more than its code. By the time it ships you should hold a coherent,
curated corpus — a **product bible** — that captures *why* the product exists, *who*
it's for, *how* it's built, and *how* it's sold:

- **Business / GTM** — Vision · Competitive Intelligence · Gartner summaries ·
  Competitor analysis · AI strategy · Roadmap · Sales arguments · RFP response
  templates · Demo scenarios · Pilot setup guides.
- **Product** — PRDs · SRSs · Personas · Glossary · UX principles · Design spec.
- **Engineering** — Domain model · API standards · Rule DSL · ADRs · Architecture ·
  Test strategy · Scenario set · RTM · Release decision.

Two things were missing before this: VibeFlow produced *some* of these (PRD, ADRs,
architecture, design-spec, test-strategy, …) but they were **scattered**
(`docs/`, `design/`, `.vibeflow/reports/`, `docs/adr/`), and there was no curated,
single view of the whole corpus — nor a notion of which docs are **living** (grown
across the project) vs **static** (written once).

## Lifecycle: living vs static

- **Living** docs are grown each phase/cycle as the product evolves — glossary,
  domain model, personas, ADRs, roadmap, API standards, Rule DSL, vision,
  competitive intelligence. They start small at intake and accrete.
- **Static** docs are produced once for a moment — a Gartner summary, a demo
  scenario, an RFP template.

## Source: bible-native vs referenced

Each doc-type declares a `source`:

- **`vibeflow`** — VibeFlow already produces it (PRD via prd-quality-analyzer,
  ADRs via architecture-bootstrap, design-spec via design-bootstrap, test-strategy
  via test-strategy-planner, …). The bible **references it in place** — single
  source, never duplicated. A "missing" `vibeflow` doc is produced by running its
  phase, not by hand-authoring.
- **`bible`** — a bible-native doc with no VibeFlow producer yet (vision, personas,
  glossary, domain model, GTM assets, …). Authored under `docs/product-bible/`.

## Structure

The curated tree lives at **`docs/product-bible/`**:

```
docs/product-bible/
  README.md            (index — generated by /vibeflow:product-bible)
  manifest.json        (optional per-project override of the taxonomy)
  business/            vision, competitive-intelligence, gartner, competitor, ai-strategy, roadmap
  gtm/                 sales-arguments, rfp-templates, demo-scenarios, pilot-guides
  product/             personas, glossary, ux-principles, srs
  engineering/         domain-model, api-standards, rule-dsl
```

`vibeflow`-source docs stay where their skills write them (`docs/architecture.md`,
`docs/adr/`, `design/design-spec.md`, `.vibeflow/reports/*`) and are linked from
the bible index — not moved.

## The taxonomy

The canonical doc-types + their category / phase / lifecycle / source live in
`hooks/scripts/bible-manifest.json` (override per project with
`docs/product-bible/manifest.json`). It's consumed by:

- **`hooks/scripts/bible-status.sh`** — read-only; reports present vs missing per
  doc + per category.
- **`/vibeflow:product-bible`** — renders the status dashboard + scaffolds the
  `docs/product-bible/` structure with templated stubs for the missing
  bible-native docs (never overwriting, never scaffolding `vibeflow`-source docs).

## Using it

```
/vibeflow:product-bible      # see what exists vs is owed; scaffold the missing bible-native docs
```

## Roadmap (this is the foundation)

Sprint 68 ships the **foundation** — taxonomy, status, structure. The rest grows
the bible across the lifecycle:

- **Intake / ingestion** ✅ (Sprint 69, `/vibeflow:bible-intake`) — review every
  input document you bring into a project (vision, Gartner, competitor decks, an
  existing PRD/spec, persona research, …), classify it into the bible, file it
  under `docs/product-bible/<category>/` (VibeFlow-produced docs referenced in
  place), and **seed the living docs** — glossary, domain model, personas — from
  the corpus. Writes `.vibeflow/reports/bible-intake.md`.
- **Living-doc growth** ✅ (Sprint 70, `/vibeflow:bible-update`) — at each phase
  boundary phase-runner folds the phase's artifacts into the living docs the
  manifest's `growsIn` marks for that phase, so the glossary, domain model,
  personas, API standards, Rule DSL, roadmap, etc. accrete instead of going
  stale (merge-never-clobber, deduped, never-invent; surface-only, never gates).
- **Assembly / curation** ✅ (Sprint 71, `/vibeflow:bible-assemble`) — a final
  coherent export of the whole bible: a curated index
  (`docs/product-bible/README.md`) linking every canonical doc, a single-file
  export (`docs/product-bible/product-bible-export.md`), and a light
  cross-consistency curation pass (gaps / stale living docs / glossary↔domain↔PRD
  coherence — flag-only). Writes `.vibeflow/reports/bible-assembly.md`.

**The Product Bible is now feature-complete** — foundation (Sprint 68) + intake
(69) + living-doc growth (70) + assembly (71): ingest your inputs, grow the
living docs each phase, and assemble the book at the end.
