# VibeFlow v2.30.0 — project lifecycle (cycles, resume, increments)

VibeFlow knew which *phase* you were in, but not which *cycle* — so it couldn't
tell "resume a paused project" from "start fresh work," and a greenfield project
that had reached DEVELOPMENT (and therefore had source files) could be misread
as **brownfield** when you came back to it. This adds an explicit lifecycle.

## The model: cycles

A project is a sequence of **cycles** — one SDLC pass per deliverable, tracked in
`.vibeflow/state/lifecycle.json`:

- **Cycle 1 — the initial build.** Greenfield (a PRD) or brownfield (a codebase).
  This is the *only* place the greenfield/brownfield distinction lives.
- **Every later cycle — an increment.** A feature/refactor/fix/migration on the
  now-existing code.

At runtime the question is never "greenfield or brownfield?" — it's **"is there
an open cycle to resume, or did the last one ship?"** — read from cycle
**status**, not from whether source files exist.

```
no .vibeflow/        → /vibeflow:onboard        → opens cycle-1 (in-progress)
cycle in-progress    → /vibeflow:phase-runner   → RESUMES from currentPhase
cycle completed (GO) → new branch + /vibeflow:brownfield-intake → opens cycle-N
```

## What changed

- **`onboard` resume-guard (Step 0).** On an already-onboarded project it no
  longer re-initializes — it routes you to `phase-runner` (resume an in-progress
  cycle) or `brownfield-intake` (a new increment, if the last cycle shipped).
  **This fixes the reported bug:** a *paused* greenfield project was being
  treated as brownfield on return because it had source files. File presence is
  no longer the signal; cycle status is.
- **`phase-runner` reads `lifecycle.json` first.** In-progress → resume;
  completed → breadcrumb the next increment on a fresh branch. And **DEPLOYMENT
  closes the cycle** on a GO release (`release.decision.go` +
  `deployment.verified` + `consensus.deployment.approved`): it marks the cycle
  `completed`, moves it to `history[]`, and breadcrumbs the PR merge + next
  increment.
- **One cycle = one branch / one PR**, track-and-breadcrumb. VibeFlow records the
  `branch`/`prUrl` per cycle and *suggests* the `git`/`gh` commands — it doesn't
  run outward-facing git for you. So each increment is tracked under its own PR,
  never mixed into the finished one.
- **`brownfield-intake`** opens an increment cycle when you start fresh work.

Docs: `docs/LIFECYCLE.md`. Pinned by `tests/integration/sprint-42.sh` (28
assertions, including a runtime routing probe over no-lifecycle / in-progress /
completed states).

## After updating

Existing projects (no `lifecycle.json` yet) are backfilled with an in-progress
cycle from their current phase on the next `onboard`/`phase-runner` run — so a
project you paused mid-flight resumes cleanly instead of looking brownfield.
