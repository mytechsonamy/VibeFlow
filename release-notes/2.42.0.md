# VibeFlow v2.42.0 — a "UI never render-verified" debt signal

v2.41.0 added `frontend-render-check` so a UI increment actually renders + is
compared to its design. But it runs only when the **current** increment is
UI-facing — and that leaves a gap an operator spotted: ANTOS's dashboard, built
back in cycle-3 (before the visual-testing tooling existed), had **never once
been opened in a browser or compared to its Figma design**, and the cycles since
were all backend, so it stayed buried. Nothing flagged it.

## What's new

A read-only reader, `hooks/scripts/ui-verification-debt.sh`, answers one
question: does this repo have a web UI that's never been render-verified, or
whose verification is stale?

- **`never`** — a web framework + a web entry are present, but there's no
  `frontend-conformance.md` (the `frontend-render-check` output).
- **`stale`** — the report exists, but a UI source file changed after it.
- **`verified`** / **`no-ui`** — quiet.

`phase-runner` Step 0 and `flow-status` now surface it:

> ⚠ web UI never render-verified — run `/vibeflow:frontend-render-check`
> (or "re-run" when stale)

It is **surface-only**: it never blocks, never auto-runs, and says nothing on a
backend-only repo or one that's already verified — so it can't become noise. It
exists to make sure a UI can't silently stay unrendered for cycles on end.

Pinned by `tests/integration/sprint-54.sh` (static + runtime probes across
no-ui / never / verified / stale / backend-only).

## For ANTOS

`/vibeflow:flow-status` (or the next `phase-runner` run) will now flag the
dashboard as never render-verified — a one-off `/vibeflow:frontend-render-check`
on it (when you next touch the UI, or as a deliberate pass) catches the
won't-boot `%20` alias bug and the Figma-vs-localhost divergence.
