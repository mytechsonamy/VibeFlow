# VibeFlow v2.23.0 — design-bootstrap: compare both, and know when DESIGN isn't UI

A follow-up to v2.22.0, driven by running the new DESIGN guide on two real
projects side by side: a UI-heavy financial product (AntOS) where the menu fit
perfectly, and a backend infra/ops increment (FlowBridge Faz 3) where a
UI-first menu was the wrong tool. v2.23.0 closes both gaps and adds a
compare-two-directions option.

## Two new design sources + a classification step

`design-bootstrap`'s menu goes from 3 options to 5, and it now classifies the
increment first.

### Step 1b — is this increment UI-facing?

DESIGN is VibeFlow's **UI/UX** phase; technical design is ARCHITECTURE's job.
But a DESIGN phase entered for a backend/infra/ops increment has little UI to
design. So before the menu, `design-bootstrap` checks the signals:

- **UI** → screens / pages / forms / dashboards, a UI-ish `platform`.
- **Backend** → API / service / pipeline / Postgres / K8s / RLS / WORM / ops,
  no screen inventory.

If it's backend-heavy, the menu leads with a flag: "this looks
backend/infra-heavy — option 5 (technical design) likely fits; the UI options
may not, and heavy *technical* design belongs in the ARCHITECTURE phase." It
**still asks** — never auto-decides.

### Option 4 — Both (compare Claude-native vs Figma)

For when the look matters enough to weigh two directions before committing:

1. Produces a Claude-native design **and** a Figma design into
   `design/candidates/`.
2. Writes a side-by-side **`design/design-comparison.md`** — visual direction,
   token systems, layout / information architecture, fidelity, accessibility,
   effort / hand-off trade-offs, and a recommendation. (`db_compare_impl` adds a
   dimension/identity check when both have screenshots.)
3. You pick the one to carry forward — or "merge: tokens from X, layout from Y."
   The chosen candidate becomes the canonical `design/design-spec.md`.

### Option 5 — Technical design (low/no-UI increment)

Writes `design-spec.md` as a **technical** design (components/services, data
model, interfaces, sequences, infra/ops, non-functionals) instead of a UI
design — with an honesty check: if it's heavy architecture, it recommends doing
it in the ARCHITECTURE phase (ADRs) instead. No tokens/wireframes — there's no
UI to design.

## Why

Running the same DESIGN step on AntOS (UI product) and FlowBridge (backend
increment) showed the skill assumed DESIGN = UI. AntOS's clean menu was right;
FlowBridge needed phase-runner to *ad-hoc* reason its way to "write a technical
spec instead." Now the skill itself handles both, and adds the compare-both
path for UI products where you want to see two directions.

Whichever you pick, the output contract is unchanged: `design/design-spec.md`
(primary) + evidence under `design/`, the consensus marker, and
`▶ Next: /vibeflow:phase-runner`. Docs: `docs/DESIGN-PHASE.md`. Pinned by
`tests/integration/sprint-35.sh`.
