# VibeFlow v2.0.0 — Filesystem-only state store

**Breaking change.** Sprint 11 retires the SQLite (solo) and PostgreSQL
(team) backends. State is now file-backed at
`.vibeflow/state/<project>/`. Every mutation writes an event JSON+MD
twin under `events/`; completed phases migrate to `archive/`. Git
versions the whole thing for free and `cat` is enough to read it.

## Why

The previous design carried a full database abstraction layer for what
is effectively one row per project. The SQLite build pulled
`better-sqlite3` (native compile), and team mode required a running
Postgres with a connection-pool probe for PgBouncer. For a CLI that
mostly wants to know "what phase are we in?" that was overkill.

The filesystem store keeps the same `StateStore` interface (so no skill
or hook changes were needed upstream) and preserves every concurrency
guarantee:

- `KeyedAsyncLock` (in-process serialization) — unchanged.
- Cross-process serialization — `proper-lockfile` replaces the pg
  advisory lock and SQLite WAL modes. 5-process race test lives at
  `mcp-servers/sdlc-engine/tests/filesystem-race.test.ts`.
- Bug #6 (lost concurrent writes) and Bug #13 (getOrInit fast-path on
  an existing row) regression tests were ported verbatim and run against
  the new backend.

## Migration

Existing installs with a populated `.vibeflow/state.db` have two paths:

### Option A — Start fresh (recommended if the project isn't load-bearing)

```bash
rm -rf .vibeflow/state.db .vibeflow/state.db-wal .vibeflow/state.db-shm
```

Next `sdlc_get_state` seeds a fresh project.json at revision 1.

### Option B — Preserve your existing rollup

```bash
bin/migrate-state-db-to-fs.sh --dry-run   # preview what will be written
bin/migrate-state-db-to-fs.sh             # write + rename state.db → .bak
```

The migrate script reads every `project_state` row, writes
`.vibeflow/state/<projectId>/project.json` + a numbered
`project_imported` event (seq = existing revision, so the next live
write lands naturally at `rev+1`), and renames `state.db` to
`state.db.migrated-<timestamp>.bak`. Re-running after migration is a
no-op.

Per-event history cannot be reconstructed from the rollup-only SQLite
schema; the `project_imported` event documents this explicitly so an
operator who later opens the audit trail knows why events before the
migration are missing.

### Recovery tool

If `project.json` ever gets corrupted, rebuild it from the event log:

```bash
bin/replay-events.sh <projectId>           # overwrite project.json
bin/replay-events.sh <projectId> --check   # diff without writing
```

The replay routes through `FilesystemStateStore.rebuildRollup()`, so
the reconstructed JSON matches what the live engine would have written
byte-for-byte.

## Added

- `mcp-servers/sdlc-engine/src/state/filesystem.ts` —
  `FilesystemStateStore` + `proper-lockfile` cross-process guard +
  per-attempt unique tmp path (so concurrent startup sweeps never wipe
  an in-flight writer's staging file) + 30 s tmp-orphan grace period.
- `mcp-servers/sdlc-engine/src/state/events.ts` — `StateEvent`
  discriminated union (`project_created`, `criterion_satisfied`,
  `consensus_recorded`, `phase_advanced`, `project_imported`) +
  `deriveEvent` / `renderEventMd` / `parseEventMd` /
  `serializeEventJson` / `parseEventJson`.
- `bin/migrate-state-db-to-fs.sh` and `bin/replay-events.sh`.
- `tests/integration/sprint-11.sh` — 20 assertions covering the
  migration round-trip and replay rebuild.
