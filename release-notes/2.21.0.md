# VibeFlow v2.21.0 — configurable per-reviewer-CLI timeout

The parser saga (v2.20.2→.4) is closed: codex's structured verdict now flows
through cleanly. This release lands the one remaining follow-up from that
debugging arc — a config knob for the reviewer-CLI timeout.

## Added: `consensus.cliTimeoutSeconds` (default 90)

The headless consensus runner and the orchestrator give each reviewer CLI a
fixed budget before recording a timeout. That budget was **hardcoded at 90s**.

On a large primary artifact — e.g. an 87KB PRD — a reviewer (gemini, in the
field) can legitimately exceed 90s. A timed-out reviewer is recorded as a
conservative `REJECTED`, and with another reviewer raising criticals that can
flip the whole aggregate to **REJECTED / agreement 0** — a flaky false-rejection
that has nothing to do with the artifact's quality.

The timeout is now config-driven:

```jsonc
// vibeflow.config.json
{
  "consensus": {
    "cliTimeoutSeconds": 180   // default 90; range 10–900
  }
}
```

- Added to `ConsensusConfigSchema` (Zod, range-validated, unit-tested).
- Read by `consensus-run.sh` and the `consensus-orchestrator` prose via
  `vf_config_get '.consensus.cliTimeoutSeconds'` (falls back to 90 when unset
  or out of the safe range).
- Pinned by `tests/integration/sprint-31.sh [S31-C]` (config-driven wiring,
  no hardcoded `vf_run_timeout 90` on a reviewer).

### When to bump it

If you see a reviewer recorded as `cli_timeout` (a `REJECTED` you didn't
expect) on a big artifact, either raise `cliTimeoutSeconds`, or shrink the
reviewer prompt with `consensus.excerptTokenBudget`. Re-running often clears a
one-off timeout too (LLM latency varies).

## Compatibility

Pure addition — default 90 preserves prior behaviour exactly. No change to the
verdict math, the parser, or any other flow. Surfaced in a live AntOS run.
