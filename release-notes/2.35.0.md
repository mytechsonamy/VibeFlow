# VibeFlow v2.35.0 — codex verdicts stop getting dropped (the parser bug, for good)

A bug that kept needing a re-patch every release: in headless consensus, **codex
was recorded as a content-free REJECTED / NEEDS_REVISION** (0 criticals, 0
suggestions, empty rationale) even though it returned a full, substantive verdict.
The specialist→apply loop then ran blind, consensus pinned at agreement 0.5, and
nothing converged. Diagnosed end-to-end on a live ANTOS run.

## Root cause

`consensus-run.sh` (and the orchestrator) captured the reviewer CLIs with
**`2>&1`**, merging **stderr into stdout**. codex `exec` writes its banner **and a
verbatim echo of the prompt** to **stderr** — and that prompt contains the JSON
**schema template**:

```
Output ONLY valid JSON matching: {verdict:APPROVED|NEEDS_REVISION|REJECTED, …}
```

which is **invalid JSON**. On a large / interleaved diff, that template landed in
the parsed blob ahead of codex's real answer, defeated `vf_extract_json`, and
dropped us into the keyword-grep fallback — which checks `REJECTED` first and
matches the `REJECTED` in the echoed template → a bare, content-free REJECTED that
flipped the aggregate.

## Fix (three layers)

1. **Capture stdout only** (root cause). codex's real verdict is on **stdout**;
   the banner + prompt-echo are on **stderr**. We now redirect stderr to a
   separate file (`2>"$errfile"`) — the schema template never enters the verdict
   blob, and `warn_cli_error` still gets the stderr for diagnostics on a real
   failure.
2. **Keyword-grep defense-in-depth.** If the fallback ever runs, it first drops
   any line containing the `|`-alternation schema template, so a stray template
   can't bias the verdict toward REJECTED.
3. **Walk-all-objects extractor (kept from v2.20.4).** `vf_extract_json` still
   returns the first balanced object that is valid JSON **and has a `.verdict`
   key**, skipping the template and any non-verdict object.

Applied to both `consensus-run.sh` and the `consensus-orchestrator` prose, for
codex and gemini.

## Why it kept coming back

v2.20.2/.3/.4 chased the *extraction* side (fence-stripping, duplicate-object,
prompt-echo) and got the extractor robust — but the **`2>&1` capture** was the
upstream cause feeding it poison. v2.35.0 fixes the capture, so there's nothing
to extract around. Pinned by `tests/integration/sprint-47.sh` with runtime probes,
so it can't silently regress again.
