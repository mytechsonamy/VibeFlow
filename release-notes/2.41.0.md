# VibeFlow v2.41.0 — actually render the UI and compare it to the design

The "dark tunnel": a web UI passes every unit + component test, the SDLC marches
on, and nobody has ever *seen the screen*. An operator hit it head-on — the
implemented ANTOS screen had **no relation** to its Figma design, and the dev
server wouldn't even start on a path with spaces (a `%20`-encoded alias). The
test suite caught none of it, because none of it ever rendered the app.

## New: `/vibeflow:frontend-render-check`

Runs in TESTING for a web UI increment, **first** in the front-end battery:

1. **Boots the front-end.** Detects the framework (Vite / Next / CRA / …) and
   starts the dev server. A server that **won't start** — a broken alias, a
   path-with-spaces, a missing env, a TS error — is a real **finding** (BLOCKED),
   not an environment glitch. This alone catches the class of bug that ships
   because nobody ran the app.
2. **Serves mock data.** No live backend needed — the screens render with
   realistic content and the key states (loading / empty / error / offline /
   gated).
3. **Captures and *surfaces* the screens.** Screenshots of each hero screen, shown
   to you (and the live `http://localhost:<port>/` to open in Chrome) — never a
   bare "rendered ✓". End of dark tunnel.
4. **Compares implemented vs designed.** The Figma frames via
   `design-bridge db_compare_impl`, or the design-spec mockups + tokens (palette
   / fonts / spacing / layout). The divergence comes out as a **concrete, named
   list, side-by-side** — so "the screen has no relation to the design" is
   actionable, not a vibe.

Verdict: `BLOCKED` when it won't boot **or** the implementation has no meaningful
relation to the design (a real "rebuild this screen against the design" signal).

## Mock now, live later

`frontend-render-check` uses **mock data on purpose** so design conformance runs
in TESTING without infra. The **front-end + real backend** integration — the UI
driving a live API end-to-end — stays `uat-executor` against a staging
environment in DEPLOYMENT. Two tiers: render + conform against mocks now; live
front+back later.

Registered in `phase-policy.json`; runs first in the phase-runner TESTING
front-end battery (its screenshots feed `visual-ai-analyzer`); arm-on-pass;
graceful-degrades to an "open it in Chrome yourself" breadcrumb when no headless
browser is available. Docs: `docs/FRONTEND-TESTING.md`. Pinned by
`tests/integration/sprint-53.sh`.
