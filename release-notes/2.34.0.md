# VibeFlow v2.34.0 — a merged PR is not a finished cycle

A live ANTOS run pushed a greenfield project's Sprint-1 increment, merged its PR,
and parked at DEPLOYMENT — and the session then suggested "start the next
increment with `brownfield-intake`." The project wasn't finished. This tightens
the lifecycle guidance so that doesn't happen.

## What was actually right

The Sprint-42 state machine worked: when `phase-runner` ran, it read the cycle as
`in-progress` at DEPLOYMENT and **resumed** — it did *not* treat the project as
brownfield. The bug was in the *narrative*, not the state.

## What was wrong

The model conflated **"PR merged + reached DEPLOYMENT (the last phase)"** with
**"cycle shipped → next increment."** They're not the same. A cycle is
`completed` **only** when its `status` flips on **DEPLOYMENT GO**
(`release.decision.go` + `deployment.verified` + `consensus.deployment.approved`).
A merged PR, or merely reaching the last phase, is **not** completion.

## The fix (guidance, loudly)

`phase-runner` Step 0, the DEPLOYMENT-close note, `onboard` Step 0, and
`docs/LIFECYCLE.md` now state explicitly:

- `completed` means the **literal status field** — not "the PR was merged", not
  "it reached DEPLOYMENT", not "the code is done".
- An `in-progress` cycle parked at DEPLOYMENT **resumes**; **never** narrate or
  breadcrumb a new increment / `brownfield-intake` for it.
- **Stuck DEPLOYMENT** (the common case — no real CI / deploy / health infra, so
  `deployment.verified` can't pass): that's a legitimate `in-progress` state.
  Two honest options — **finish the deploy** (wire the pipeline → GO), or the
  **operator explicitly closes/defers** the cycle (set `status` with a note like
  "shipped to repo; deploy deferred"). **Do not** auto-start a new increment to
  "move on" — that silently abandons the open cycle.

Pinned by `tests/integration/sprint-46.sh`. No engine change — the state machine
was already correct.
