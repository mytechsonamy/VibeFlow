# VibeFlow v2.32.0 — guaranteed front-end testing for UI changes

Coverage + mutation tell you the *tests* are good — not that the **UI** is right.
For a UI change you also need: every field matches the design, every input is
validated, every function works end-to-end and meets its requirement. v2.32.0
makes that a guaranteed gate, not an optional set of skills you remember to run.

## New: `/vibeflow:input-validation-matrix`

The biggest gap was systematic **data validation**. The new skill builds, *for
every input field*, the full matrix:

- **Required / presence** — empty / whitespace / missing → the field's message shows.
- **Type** — alpha in a numeric field, decimals in an integer, letters in a date → rejected.
- **Boundary** — min / min-ε / max / max+ε / zero / negative; minLength / maxLength ± 1.
- **Format** — valid vs malformed (email, IBAN checksum, phone, currency precision/separator).
- **Enum / allowed set**, **cross-field** ("amount ≤ balance", "confirm == value").
- **Injection / safety** — `<script>…`, `' OR 1=1`, unicode/RTL, oversized → escaped or rejected, never executed/stored raw (hard BLOCKED for financial/healthcare).
- **Output control** — the accepted value is formatted/masked as the spec says.

It writes **runnable tests into the project suite** (component + form-submit
E2E) and a `validation-matrix.md` report. A rule with *no wired validation* is
reported as a defect, not just a test gap.

## The UI-conditional front-end battery

phase-runner's TESTING walk now detects whether the active increment is
**UI-facing** (change-type `ui`/`mixed`, or a `design/design-spec.md` exists). If
so, it runs the full battery on top of coverage + mutation:

| Concern | Lane |
|---|---|
| Each field matches the design | `visual-ai-analyzer` (+ Figma `db_compare_impl`) |
| Data validation | **`input-validation-matrix`** |
| Functions work (E2E) | `e2e-test-writer` (Playwright / Detox) |
| Functions meet requirements | `business-rule-validator` + `traceability-engine` |
| End-to-end on staging | `uat-executor` |

A **backend / infra** increment skips the battery — coverage + mutation only,
unchanged.

## Why it's a guarantee

The validation + E2E tests live **in the project's own suite**, so the existing
gates enforce them: they must pass (`regression-test-runner` / `quality-gates`)
and count toward `coverage.met`. The battery's reports become evidence for
`consensus.testing.approved`. So a UI increment can't reach a GO release without
the front-end battery green.

## Out of scope: A/B

A/B testing is a *production experiment* (two variants measured live), handled by
the `observability` MCP — not a pre-release gate. The battery guarantees both
variants are correct and validated before they ship; picking the winner is a
runtime measurement.
