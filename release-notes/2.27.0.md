# VibeFlow v2.27.0 — the brownfield on-ramp

VibeFlow's SDLC begins at REQUIREMENTS, which assumes a PRD to score. That fits
a greenfield product — but on a **brownfield** project you already have code,
and you're almost never rebuilding the whole thing: you're doing an
**increment** (a feature, refactor, bug-fix, migration). There was no guided way
to get from "I have a codebase + I want to do X" to a requirements doc the SDLC
could run. Now there is.

## Added: `/vibeflow:brownfield-intake`

Run it right after `onboard` on a project that already has code. (And `onboard`
now points you there automatically when it detects a codebase.)

**1 — It understands the code first**, so you don't have to explain it. It
fingerprints the repo via the `codebase-intel` MCP — languages, frameworks, test
runners, module layout, the import graph + cycles, churn×complexity hotspots,
and tech-debt markers — into `.vibeflow/reports/codebase-fingerprint.md`.

**2 — It asks how you want to define the work — four ways:**

| # | Path | You give |
|---|---|---|
| 1 | **Describe it** | plain-language intent — the fastest start |
| 2 | **Point to a doc** | a path to an existing requirements/spec/ticket file |
| 3 | **Guided Q&A** | answers to goal / change-type / area / acceptance |
| 4 | **From an issue** | a GitHub/GitLab issue (`gh`/`glab` by number/URL) or pasted text |

**3 — It synthesizes a code-anchored, increment-scoped requirements doc**
(`docs/<increment>-requirements.md`): goal, explicit in/out scope, the modules
it touches (from the dependency graph), the patterns to follow, the hotspots/debt
it lands near, a **change-type classification** (UI / backend / infra) with the
phase implications, functional + acceptance criteria, compatibility constraints,
and risks.

**4 — It hands off** to `prd-quality-analyzer` → `phase-runner`, scoped to the
increment — not the whole product.

## Why the classification matters

The increment's nature routes the later phases, and `brownfield-intake` says so
up front:

- **Backend / infra increment** → DESIGN is a *technical* note (`design-bootstrap`
  option 5, not UI), and the architecture is mostly fixed by the existing code
  (`architecture-bootstrap` "stack-agnostic / incremental").
- **UI increment** → DESIGN is central.

This is exactly what FlowBridge did by hand — a backend "Faz 3" increment on a
branch — now a first-class flow.

Docs: `docs/BROWNFIELD.md`. Pinned by `tests/integration/sprint-39.sh`.

## Prerequisites

`codebase-intel` ships with the plugin. For the issue path, `gh` (GitHub) or
`glab` (GitLab) on PATH if you want to pull by number/URL — otherwise paste the
ticket text.
