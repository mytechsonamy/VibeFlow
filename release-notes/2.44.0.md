# VibeFlow v2.44.0 — phase-runner stops tripping its own consensus-gate

A recurring papercut: you run an analyzer (say `prd-quality-analyzer`), it passes
and arms the consensus marker — then you run `/vibeflow:phase-runner`, and its
**very first action** throws:

```
PreToolUse:Bash hook error: consensus-gate: a pending cross-AI consensus review
is blocking this tool call.
```

phase-runner is the thing that *runs* consensus and drains the marker — but its
read-only **setup** (reading lifecycle state, `git status` to surface in-flight
work, the UI readers) is Bash, and `consensus-gate` blocks all Bash until
consensus runs. So the session would recover with a `VF_SKIP_CONSENSUS_GATE=1`
dance every time.

## Fix (two parts)

1. **phase-runner reads setup state with ungated tools.** Step 0 now reads
   `lifecycle.json` with the **Read tool** and the engine phase via **MCP**
   (`sdlc_get_state`) — not `cat`/`jq` in Bash. Reading state was never something
   the gate should block.

2. **The gate allowlists read-only inspection.** `consensus-gate` now lets
   VibeFlow's own read-only readers (`ui-verification-debt.sh`,
   `ui-styling-check.sh`, `loop-audit.sh`) and read-only `git status` /
   `git rev-parse` through — they only *inspect* state, so they can't "move past"
   the consensus requirement, and blocking them was pure friction.

A **write** (`> src/foo.ts`) or forward work (`npm run build`) under an armed
marker still blocks — the gate's actual purpose (force consensus before moving
forward) is intact.

So `/vibeflow:phase-runner` right after an analyzer now gathers state and runs
consensus cleanly, no hook error and no `VF_SKIP` workaround. Surfaced on a live
ANTOS cycle-6 run. Pinned by `tests/integration/sprint-56.sh` (static + runtime:
readers/git allow, writes/forward-work block).
