# VibeFlow v2.19.0 — onboarding clarity + a phase-runner that really runs

Sprint 31. Two operator-facing papercuts, surfaced by a real first-run
session on a fresh project, are now fixed — plus the architectural
contradiction underneath them.

## ⚠️ Breaking: `/vibeflow:init` → `/vibeflow:onboard`

VibeFlow's project-bootstrap skill was named `init`, colliding with Claude
Code's built-in `/init`. Typing "init" in the command picker was
ambiguous, and operators who installed the plugin without wanting the SDLC
flow got the two confused. It is now **`/vibeflow:onboard`**.

- No deprecation shim — a lingering `init` skill would just re-create the
  collision. Update any muscle memory / scripts to `/vibeflow:onboard`.
- Behaviour is otherwise identical (REQUIREMENTS-only, `disable-model-invocation`,
  same config + `.vibeflow/` scaffolding).

## `▶ Next:` breadcrumbs

Every phase-flow skill now ends with a single copy-pasteable
`▶ Next: /vibeflow:<command>` line as its **last** output line, so the
next step is never a guess. The canonical first-run sequence is now
self-describing: `onboard → prd-quality-analyzer → phase-runner`. See the
new [docs/ONBOARDING.md](../docs/ONBOARDING.md).

## phase-runner actually drives consensus now (no more deadlock)

The headline bug: `/vibeflow:phase-runner` advertised a one-command
analyzer → consensus → advance walk, but **structurally could not
complete it**. The consensus chain (`consensus-orchestrator`,
`-specialist`, `-arbiter`, `apply-arbiter-patch`, `advance`) is all
`disable-model-invocation: true`, so the model cannot fork it. Worse, the
analyzer's `consensus-needed.json` tripped `consensus-gate` and blocked
every subsequent tool call — including phase-runner's own next step.
Result: an immediate hard stop ("BLOCKED — consensus chain un-invokable").

Root contradiction: Sprint 14-16 made consensus **operator-gated**
(un-forkable + gate hook); Sprint 19 promised phase-runner is a **one-command
autonomous walk**. Both couldn't be true.

The fix keeps both guardrail and autonomy by splitting the two execution
contexts:

- **New `hooks/scripts/consensus-run.sh`** — the headless equivalent of
  the orchestrator's external-CLI pipeline. It resolves the primary
  artifact, runs every reviewer CLI on PATH (codex, gemini), and finalises
  a real `verdict.json` via a new additive **`consensus-aggregator.sh
  --finalize`** mode (no 600s quorum stall — the panel is exactly the CLIs
  that ran), feeding the same history.jsonl / reviewer-memory / auto-revert
  machinery. It drains `consensus-needed.json` so the gate unblocks.
- **`phase-runner`** now calls that script as plain Bash (no un-forkable
  skill in the path). On **APPROVED** it records consensus + auto-advances
  via the sdlc-engine MCP tools — a true one-command walk. On
  **NEEDS_REVISION / REJECTED** it stops with an honest breadcrumb to the
  operator-confirmed specialist → arbiter → apply chain (those rewrite the
  PRD/ADR and stay human-owned by design). Autonomy stops at the verdict.
- **`consensus-gate.sh`** allowlists `consensus-run.sh` (it IS the drain
  action).

When you invoke `/vibeflow:phase-runner` you are the human authorising the
walk, so running the real reviewer CLIs preserves the Sprint 16 intent —
no fabricated verdicts. The interactive `/vibeflow:consensus-orchestrator`
is unchanged: full 3-AI panel (adds `claude-reviewer`) with iterative
negotiation, for when you want the deeper review by hand.

> If neither codex nor gemini is on PATH, headless consensus can't run
> (claude-reviewer is model-only); phase-runner points you at the
> interactive orchestrator.

## Compatibility

- The interactive consensus path, the SubagentStop aggregator path, and
  every existing consensus integration suite (sprint-14/15/16/17/19/23/28/30)
  are unchanged and green.
- Only new commands surface (`onboard`); no config schema change.
