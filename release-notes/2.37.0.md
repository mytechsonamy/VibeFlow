# VibeFlow v2.37.0 — a `>` in a criterion name no longer blocks the gate

A live ANTOS cycle-2 advance hit a subtle one: the REQUIREMENTS gate stayed
**blocked even though `testability.score>=60` showed as satisfied**.

## What happened

Exit criteria like `testability.score>=60` contain `>` (and some have `<`).
Somewhere in transit — the model emitting the tool call, or a serialization
layer — the name got **HTML-escaped**, so `sdlc_satisfy_criterion` stored
`testability.score&gt;=60`. The exit gate checks the **literal**
`testability.score>=60`, so the two never matched and `/vibeflow:advance` refused.
It would bite any criterion containing `>`, `<`, or `&`.

## The fix

The engine now **normalizes HTML entities** on the single write path
(`satisfyCriterion`) before storing the criterion:

- `&gt;`→`>`, `&lt;`→`<`, `&quot;`/`&#39;`/`&apos;`→quotes, `&amp;`→`&` (decoded
  last so a double-escaped entity collapses correctly), plus a trim.

So the satisfied set is always the canonical literal and matches the exit gate in
`phases.ts`, regardless of any escaping upstream. VibeFlow can't stop a caller
from escaping, but it canonicalizes at the boundary so it never bites again.

`normalizeCriterion` is exported and unit-tested; sdlc-engine tests 201 → 202.
Pinned by `tests/integration/sprint-49.sh` (static + a live node probe that
`testability.score&gt;=60` → `testability.score>=60`).

## After updating

If you previously re-satisfied a criterion with the literal name to unblock an
advance, you no longer need to — the escaped form is canonicalized on store.
