# VibeFlow v2.10.0 — Close the Action Gap

**Sprint 22.** The L3 slow loop has *observed* (Sprint 20 learning-loop)
and *framed* (Sprint 20-G decision-recommender) since v2.8.0 — but it
never *acted*. A recommendation like "raise `consensus.maxIterations` —
REQUIREMENTS keeps needing 3 rounds" was read, framed, and then left for
the operator to hand-edit. v2.10.0 closes that **action gap**.

## The `learning-apply` skill

New `/vibeflow:learning-apply [--dry-run] [--yes]` — the
`consensus-arbiter` of the slow loop. It reads
`.vibeflow/reports/consensus-learning-report.md` and classifies each
finding into three lanes:

- **config-tune** — the recommendation names a typed `vibeflow.config.json`
  key (`consensus.maxIterations`, `excerptStrategy`,
  `reviewerMemory.compaction`, …) → a **diff-first patch** under
  `.vibeflow/state/patches/learning-<ts>/`.
- **template-route** — a `recurring-suggestion-theme` (an upstream
  template gap) → a `/vibeflow:consensus-specialist` dispatch
  recommendation (REQUIREMENTS → `prd-rewriter`, ARCHITECTURE →
  `adr-author`, …). `learning-apply` does **not** auto-fork the
  specialist.
- **escalate** — everything else → `decision-recommender`.

## Propose-only, by design

`learning-apply` **never writes `vibeflow.config.json` or source
directly** — its only writes are patches + the audit report
`.vibeflow/reports/learning-apply-decisions.md`. Config changes land
only through `--yes`, and only after three safety gates:

1. **Evidence floor** — findings below `learningApply.minObservations`
   (default 3) are skipped.
2. **Bounded** — a numeric tune moves at most
   `learningApply.maxRelativeStep` (default ±50%) and is clamped to the
   field's schema range.
3. **Schema re-validation** — the patched config is parsed through the
   engine's `EngineConfigSchema` before apply; an out-of-range or
   wrong-enum result is **rejected**, never applied.

Why propose-only? The loop tunes the very machinery that governs quality
gates — a bounded-but-autonomous tuner that drifts `approvalThreshold`
down is exactly the "gate-suppression-creep" the learning loop exists to
*catch*. A human stays in the loop on every config change. Bounded
auto-apply is deliberately deferred (Sprint 23+).

## Configuration

```jsonc
{
  "learningApply": { "enabled": true, "maxRelativeStep": 0.5, "minObservations": 3 }
}
```

Fully defaulted + partial-merge friendly (`LearningApplyConfigSchema`).

## Upgrade

```
/plugin uninstall vibeflow@vibeflow
/plugin install vibeflow@vibeflow
/reload-plugins
```

No migration. `learning-apply` is additive and propose-only — it changes
nothing until you invoke it with `--yes`.
