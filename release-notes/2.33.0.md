# VibeFlow v2.33.0 — mobile crash & stability testing (Expo-aware)

Functional E2E tells you the flows work. On mobile — and on Expo especially —
that's not where it breaks: the app crashes at **cold start** (a native-module /
`app.config` / env mismatch) or on a lifecycle event (backgrounding, low memory,
a denied permission, a dropped request mid-flow). v2.33.0 adds a dedicated crash
lane for exactly that.

## New: `/vibeflow:mobile-stability-runner`

Runs in TESTING, **only when the platform is mobile** (`ios` / `android` /
`all`). It:

- **Auto-detects the runner** — Expo (`app.config`/`app.json` + `expo` dep) →
  **Maestro** (Expo Go / dev-client); bare React Native → **Detox**.
- **Runs a crash-focused battery** beyond the happy path: cold-start smoke,
  background↔foreground, low-memory, deep links, permission denial, network-loss
  mid-flow, rotation, rapid navigation, JS unhandled-rejection.
- **Detects** native crashes (process exit / tombstone), JS fatal / redbox, ANR
  — and surfaces anything a configured crash reporter (Sentry / Crashlytics /
  Expo) captured during the run.
- **Verdict:** `PASS` (no crash) → arms consensus; `BLOCKED` on a cold-start or
  P0-flow crash (non-negotiable).

## Graceful in CI, a real gate locally

With **no simulator/device/EAS** available it does **not** fail hard — it records
`NEEDS_REVISION` and breadcrumbs the local command
(`maestro test …` / `eas build --profile development` / `npx expo start`) so you
run it on your own machine. On a machine with a booted simulator, it's a real
gate. (An environment gap is not a crash.)

## Where it fits

phase-runner's TESTING walk runs it alongside the front-end battery for a mobile
UI increment; non-mobile platforms skip it. It's **pre-release crash hunting** —
production crash monitoring stays with your crash reporter + the `observability`
MCP; the two complement.
