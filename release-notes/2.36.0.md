# VibeFlow v2.36.0 — the multi-cycle lifecycle gets its engine reset

Sprint 42 taught VibeFlow to track a project as a sequence of **cycles**
(`lifecycle.json`). But the gate behind `/vibeflow:advance` and `phase-runner` —
the `sdlc-engine` MCP — still modeled a **single linear pass**. So when you
started cycle 2, `lifecycle.json` said REQUIREMENTS while the engine stayed
pinned at the previous cycle's terminal phase (DEPLOYMENT), and `phase-runner`
refused on a phase-mismatch. There was no way to reset it: `advance_phase`
DEPLOYMENT→REQUIREMENTS is (correctly) rejected as a backward transition.
Surfaced on a live ANTOS run opening cycle-2 (Wealth Aggregation).

## New engine tool: `sdlc_start_cycle`

It opens a new SDLC cycle on the engine:

- resets `currentPhase` to **REQUIREMENTS** (the first phase),
- clears satisfied criteria + last consensus,
- bumps a new `ProjectState.cycle` counter (1 = initial build, 2+ = increments).

It is an **explicit, audited cycle boundary** — not a backward rewind *within* a
cycle. The engine still refuses `advance_phase` going backward; `sdlc_start_cycle`
is the sanctioned, logged way to begin the next pass.

## Wiring (the two stores stay in sync)

- **`brownfield-intake`** calls `sdlc_start_cycle` when it opens a new increment
  cycle — so `lifecycle.json` and the engine agree from the start.
- **`phase-runner` Step 0** reconciles a *pre-existing* drift: if the engine is
  **ahead** of the cycle's phase (a cycle opened before this reset existed — e.g.
  a pre-2.36 ANTOS cycle-2), it calls `sdlc_start_cycle` once, then proceeds.

`ProjectState.cycle` is optional and back-compat (absent ⇒ cycle 1). sdlc-engine
unit tests 200 → 201; pinned by `tests/integration/sprint-48.sh`. Docs:
`docs/LIFECYCLE.md`.

## After updating (e.g. ANTOS cycle-2)

A cycle-2 that stalled at the engine gate now walks cleanly: `brownfield-intake`
(or `phase-runner` Step 0) resets the engine to REQUIREMENTS, and
`/vibeflow:phase-runner` runs the new increment from the start.
