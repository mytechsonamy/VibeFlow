# VibeFlow v2.5.3 — `.mcp.json` `${CLAUDE_PLUGIN_ROOT}` fix (critical)

**Fixes the bug that made every MCP-backed skill silently inert
when the plugin was installed in a consumer project.**

## Symptom

You install the VibeFlow plugin in another project. `/reload-plugins`
reports "5 plugin MCP servers loaded". But `/vibeflow:advance`
can't find `sdlc_advance_phase`, `/vibeflow:status` comes back
degraded with "no project.json", and every other MCP-dependent
workflow fails quietly.

## Root cause

`.mcp.json` used bare `./` prefixes:

```json
"args": ["./mcp-servers/sdlc-engine/dist/bundle.js"]
```

Claude Code resolves these relative to the **current working
directory**, not the plugin install location. So when a
consumer project opened Claude Code from their own repo,
`./mcp-servers/...` pointed at a non-existent path in their
codebase. Node failed to load the bundle, the MCP server
reported as "loaded" at the registration layer but with no tools.

`hooks.json` already used the correct pattern
(`${CLAUDE_PLUGIN_ROOT}/...`); `.mcp.json` hadn't been updated.
In the VibeFlow repo itself the bug was invisible because `.`
happened to resolve correctly.

## Fix

All five MCP server paths in `.mcp.json` now use
`${CLAUDE_PLUGIN_ROOT}/`:

```json
"args": ["${CLAUDE_PLUGIN_ROOT}/mcp-servers/sdlc-engine/dist/bundle.js"]
```

Claude Code substitutes `${CLAUDE_PLUGIN_ROOT}` with the plugin's
actual install directory on every session start.

A new regression guard in `tests/integration/run.sh` asserts
every `.mcp.json` server uses the `${CLAUDE_PLUGIN_ROOT}/` prefix
— future commits that regress back to bare `./` fail CI.

## Upgrade

```
/plugin uninstall vibeflow@vibeflow
/plugin install vibeflow@vibeflow
/reload-plugins
```

Then restart Claude Code once to re-register the MCP servers
from the corrected paths. After restart, `/vibeflow:advance`,
`/vibeflow:status`, and every other MCP-backed skill should
surface their tools correctly in any project.
