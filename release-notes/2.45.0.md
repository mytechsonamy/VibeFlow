# VibeFlow v2.45.0 — UI test scenarios planned up front, not discovered in TESTING

A process question from a live run: *for any project — and especially when
there's a UI — do we enumerate the detailed test scenarios up front (every
field, both how it **looks** and how it behaves with **real backend data**),
write them to a doc, AI-review them, and then actually use them in the test
runs?*

The honest answer was "mostly, but with a real gap":

- **Functional** scenarios — yes, up front. `test-strategy-planner` already
  generates a happy / edge / negative scenario per requirement into
  `scenario-set.md`, and that doc **is** AI-reviewed (it's evidence on the
  PLANNING `test-strategy.md` consensus) and **is** used downstream (RTM-traced,
  consumed by the test writers and coverage analyzer).
- **UI detail** — *not* up front. The per-field **visual conformance**
  (does this field match the design — color, type, spacing, states), the
  per-field **validation** (required / type / boundary / format), and the
  **backend-data binding** (does the field render the correct server value, and
  does the screen handle loading / empty / error / offline) were only ever
  generated *inside* TESTING. So they were never part of the reviewed PLANNING
  deliverable, never RTM-traced, and the TESTING front-end battery had nothing
  concrete to implement against — it improvised the UI checks each run.

## The fix — a UI-conditional Step 2b in PLANNING

`test-strategy-planner` gains **Step 2b: UI Scenario Enumeration**. It runs only
when the increment is actually UI:

- platform is `web` or `all`, **and**
- a design spec exists (`design/design-spec.md`, found via Glob).

Otherwise it's skipped and the strategy doc records *why* (non-UI increment) —
backend/infra increments are completely unchanged.

When it runs, it reads the design spec (and tokens / mockups if present) and, for
**each hero screen and each field/control on it**, enumerates three dimensions
into a new `## UI Scenarios` block in `scenario-set.md`:

| Dimension | ID form | Asserts | Implemented in TESTING by |
|---|---|---|---|
| Visual conformance | `SCN-UI-<screen>-V-NN` | Field matches design — color/font/spacing/layout + default/hover/focus/disabled/error/loading states | `frontend-render-check`, `visual-ai-analyzer` |
| Field validation | `SCN-UI-<screen>-VAL-NN` | Per-field required / type / boundary / format / cross-field | `input-validation-matrix`, `uat-executor` |
| Backend-data binding | `SCN-UI-<screen>-DATA-NN` | Field renders the correct **server** value; screen handles loading / populated / empty / error / offline | `frontend-render-check`, `uat-executor` |

Every UI scenario is **traced back to the functional requirement** its screen
serves, so the RTM now carries the full `FR-* → screen → UI scenario` chain — the
per-field visual/data checks aren't orphaned UI trivia, they're tied to the
requirement they verify. And the coverage gap analysis gains UI-aware categories:
`UI_UNTESTED` (a design screen/field with no scenario), `UI_DATA_GAP` (a screen
that's visually checked but never verified against real server data — pretty but
unproven), and `DESIGN_REQ_GAP` (a screen with no backing requirement, or a
requirement whose UI has no screen). A stray screen is a **finding**, never a
silently invented requirement.

## What changes for you

The up-front, multi-AI-reviewed scenario set is now honest about the UI surface.
For a UI increment, **before any code is reviewed**, the plan already spells out —
per field — how it should look in each state, what it must validate, and what real
backend data it must bind and how it degrades. Those exact scenarios are then the
contract the TESTING front-end battery implements, so you're no longer "driving
through a dark tunnel" on the UI: what gets tested in TESTING is what was planned
and reviewed in PLANNING.

Surfaced by an operator asking the general process question across projects.
Pinned by `tests/integration/sprint-57.sh` (31 static checks). Skill-only change —
